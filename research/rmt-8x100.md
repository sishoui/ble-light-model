# C3 RMT 8×100 分时复用事实核查（ticket #23）

> 项目：ESP32-C3FH4 + 8 条 WS2812B（1010 封装，每条 100 颗），数据线 GPIO0/1/3/4/5/6/7/10。
> 目标：不加外部 OE / 74HCT238，靠 2 个 RMT TX 通道 4+4 分时复用，整轮刷新 76–83 Hz。
>
> **取证基线**：本机 PlatformIO 安装的 ESP-IDF **v5.5.3**（`~/.platformio/packages/framework-espidf`，`version.txt` = `5.5.3`，`package.json` = `3.50503.0`）。下文路径均相对该 IDF 根目录，`文件:行号` 形式。线上的同版本文档为 `docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32c3/`。
>
> 全文严格区分两类句子：
> - **【源码/文档】** —— 可在上面这份 IDF 或官方文档里逐行指到的内容。
> - **【推断】** —— 由源码逻辑推出、但没有官方文字确认，必须上板验证。

## 0. 结论摘要（TL;DR）

1. **可行，但对 76 Hz 目标没有余量，且必须接受一个 30 µs 级的硬实时约束。**
   理论帧率上限 **83.3 Hz**（8×3.0 ms / 2），实际含切换开销 **80–82 Hz**；对 60 Hz 有约 27 % 余量，对 76 Hz 只剩 7–8 %。

2. **本项目里"48 symbol / 60 µs 补一次"的说法是错的，真实是"24 symbol / 30 µs"。**
   驱动把 `mem_block_symbols` 的**一半**作为 ping-pong 半区（`ping_pong_symbols = mem_block_num * 48 / 2`），阈值中断也按这个半区大小设置。1 块 = 48 symbol 的通道，ping-pong = **24 symbol ≈ 30 µs**。
   现有 `research/hardware.md` §1.2 的"48 符号 = 60 µs refill 窗口"需要更正。

3. **C3 的 2 个 TX 通道不可能同时获得 >48 symbol 的内存。**
   驱动按"连续内存块"分配，`{2,2}` 这种切法第二个通道直接创建失败（`ESP_ERR_NOT_FOUND`）。可用组合只有 `{1,1}`、`{1,2}`、`{1,3}` 或**单通道 `{4}`**。而 ping-pong 窗口取决于**两个通道里较小的那个**，所以只要用 2 个通道，窗口就永远是 **30 µs**。
   ESP-IDF FAQ 给出的两条标准缓解措施（"加大 `mem_block_symbols`"、"换一个核跑 RMT"）**在 C3 上互相排斥**：加大内存就没法开第二个通道，C3 又只有一个核。

4. **`rmt_tx_switch_gpio` 只能在通道 INIT（已 `rmt_disable`）状态下调用**，不能帧中切换；实测语义（官方单测）是：切换后新引脚**立即继承上一个事务的 `eot_level`**。它有明确的"毛刺"风险点不在 RMT，而在**旧引脚被 `gpio_output_disable` 后变成高阻**——8 条线里任意时刻有 6 条悬空，必须加下拉。
   更便宜的替代是"一信号扇出 4 个 GPIO + 只切输出使能"，见 §2.4。

5. **撕开 30 µs 窗口的真实威胁不是 BLE 中断，而是 FreeRTOS 临界区。**
   C3（RISC-V）上 `portENTER_CRITICAL` 把中断阈值抬到 `RVHAL_EXCM_LEVEL = 4`，**屏蔽全部 1–3 级外设中断**，不管 RMT 配到几级。NimBLE host 的 `ble_npl_hw_enter_critical()` 就是 `portENTER_CRITICAL`。BLE 控制器 ISR 本身是 `LEVEL3 | IRAM`，把 RMT 也设成 `intr_priority = 3` 可与它同级、互不抢占；但两者都挡不住临界区。
   **会不会真的撕开 30 µs，官方没有任何文档承诺，必须实测**（§6 第 1 项）。

6. **`CONFIG_RMT_TX_ISR_CACHE_SAFE` 默认是 `n`，必须显式打开**，否则任何 flash 写（NVS 存 BLE 绑定、日志、OTA）都会把 RMT 补数 ISR 推迟到缓存恢复之后 → 必然错色。

7. **替代方案排序（结论，不铺陈）**：
   - **I2S 并行：C3 不可用**——C3 没有 LCD_CAM / I2S parallel 外设（`SOC_I2S_NUM=1`，`SOC_I2S_PDM_MAX_TX_LINES=2`）。
   - **SPI MOSI 单线：可行但不解决问题**——C3 只有 1 个通用 SPI 主机（SPI2），1 条 MOSI 只能带 1 条灯带。
   - **四线 QIO SPI 并行：硬件与驱动都允许，理论最优（8 条约 6 ms，零 CPU 占用），但没有官方例程，属于自研 DMA+位交织，风险高于 RMT**，建议作为并行的 spike，而不是首选。
   - **关中断 bit-bang 8 路并行：能力上可行（一条 GPIO 寄存器写就能同时翻 8 位），但 80 Hz 下要占掉 24 %–100 % 的 CPU 时间且全程关中断，BLE 必崩**，只作死机兜底。
   - **双缓冲/预编码：不改变 30 µs 窗口，但能把 ISR 里的工作量压到"纯 24 个字拷贝"，是本方案必须做的一环**（不是可选优化）。

8. **最大风险**：C3 单核 + 24 symbol ping-pong，任何一次 ≥30 µs 的临界区/ISR 占用都让某条灯带在帧尾**重播旧数据**（官方 FAQ 原文："would end up sending outdated data"）——不是崩溃、不是全灭，而是**局部错色、偶发闪一下**，很难复现定位。

## 1. C3 的 RMT 能力边界

### 1.1 通道数与内存（【源码】）

`components/soc/esp32c3/include/soc/soc_caps.h:244-252`：

```c
#define SOC_RMT_GROUPS                    1U
#define SOC_RMT_TX_CANDIDATES_PER_GROUP   2   // 只有 2 个通道能做 TX
#define SOC_RMT_RX_CANDIDATES_PER_GROUP   2
#define SOC_RMT_CHANNELS_PER_GROUP        4   // 共 4 个通道
#define SOC_RMT_MEM_WORDS_PER_CHANNEL     48  // 每通道 48 个 32-bit 字（= 1 个内存块）
#define SOC_RMT_SUPPORT_ASYNC_STOP        1
```

`components/soc/esp32c3/rmt_periph.c` 给出信号映射：ch0/ch1 只有 `tx_sig`，ch2/ch3 只有 `rx_sig`。**所以"2 个 TX 通道"是硬边界，不是驱动限制。**

- 每个 symbol = `rmt_symbol_word_t` = 4 字节（`duration0:15 + level0:1 + duration1:15 + level1:1`）。
- 48 symbol/块 × 4 块 = **192 个 32-bit symbol 的物理内存**，不是 48。48 只是**单通道默认/最小**占用。

### 1.2 有没有 DMA（【源码】）

`SOC_RMT_SUPPORT_DMA` 在 v5.5.3 里**只在 esp32s3 / esp32p4 的 soc_caps.h 中定义**（对 `components/soc/*/include/soc/soc_caps.h` 全量 grep 确认）。C3 上没有该宏，因此 `rmt_new_tx_channel()` 走这条分支：

`components/esp_driver_rmt/src/rmt_tx.c:252-254`
```c
#else
    ESP_RETURN_ON_FALSE(config->flags.with_dma == 0, ESP_ERR_NOT_SUPPORTED, TAG, "DMA not supported");
#endif
```

**结论：C3 的 RMT 无 DMA，TX 数据必须由 CPU 在 ISR 里逐 symbol 喂。** 这是本方案所有风险的根。

### 1.3 内存块怎么分：真实 ping-pong 是 24 symbol / 30 µs（【源码】）

`components/esp_driver_rmt/src/rmt_tx.c:113-121`
```c
    mem_block_num = config->mem_block_symbols / SOC_RMT_MEM_WORDS_PER_CHANNEL;
    if (mem_block_num * SOC_RMT_MEM_WORDS_PER_CHANNEL < config->mem_block_symbols) {
        mem_block_num++;
    }
    tx_channel->ping_pong_symbols = mem_block_num * SOC_RMT_MEM_WORDS_PER_CHANNEL / 2;
```

`rmt_tx.c:326-328`
```c
    rmt_ll_tx_set_mem_blocks(hal->regs, channel_id, tx_channel->base.mem_block_num);
    // set limit threshold, after transmit ping_pong_symbols size, an interrupt event would be generated
    rmt_ll_tx_set_limit(hal->regs, channel_id, tx_channel->ping_pong_symbols);
```

`mem_block_symbols = 48` → `mem_block_num = 1` → **`ping_pong_symbols = 24`**。

所以一次 2400 symbol 的发送是这样跑的（`rmt_tx.c:742-748` + `components/esp_driver_rmt/src/rmt_encoder_copy.c:36-49,96-105`）：

| 时刻 | 硬件指针 | 驱动动作 | 语义 |
|---|---|---|---|
| t=0 | 0 | `rmt_tx_do_transaction()` 一次性写满 48 个 symbol，启动 | 缓冲区整块是"满的" |
| t≈30 µs | 24 | 阈值中断 `rmt_isr_handle_tx_threshold()` 写 [0,24) | 半区 A 被重填，指针还在半区 B |
| t≈60 µs | 48→0 | 阈值中断写 [24,48) | 半区 B 被重填 |
| … | … | 每 24 symbol 一次 | 2400 symbol = **100 次补数** |

- **每个通道每 100 次/条 × 8 条 = 800 次阈值中断/帧**。
- **单次补数的截止时间 = 24 symbol × 1.25 µs = 30 µs**。这就是"补不及时"的全部余量，没有第二个缓冲层。

> **对 `research/hardware.md` §1.2 的更正**：那里写"48 符号产生一次阈值中断 → 60 µs refill 窗口"，把 `mem_block_symbols` 当成了阈值。按上述两处源码，正确值是 **24 符号 / 30 µs**。这不影响"必须 2 通道时分"的结论，但把实时余量直接砍半。

### 1.4 两个通道的内存组合：只有 4 种，且都换不来更大窗口（【源码】）

`rmt_tx.c:125-152` 的分配逻辑：`channel_mask = (1 << mem_block_num) - 1`，从 `j = 0` 扫到 `j = 1`（`RMT_TX_CHANNEL_OFFSET_IN_GROUP = 0`，见 `rmt_private.h:75`），要求 `channel_mask << j` 与 `occupy_mask` 不冲突，**内存块必须连续且从本通道号开始**。

先建 ch0 再建 ch1 时：

| 配置 | ch0 占用块 | ch1 占用块 | ch0 ping-pong | ch1 ping-pong | 最小窗口 | 8×100 理论帧率 |
|---|---|---|---|---|---|---|
| `{1,1}` | {0} | {1} | 24 (30 µs) | 24 (30 µs) | **30 µs** | 83.3 Hz |
| `{1,2}` | {0} | {1,2} | 24 | 48 (60 µs) | **30 µs** | 83.3 Hz |
| `{1,3}` | {0} | {1,2,3} | 24 | 72 (90 µs) | **30 µs** | 83.3 Hz |
| 单通道 `{4}` | {0,1,2,3} | 不可创建 | 96 (120 µs) | — | 120 µs | **41.7 Hz** |
| `{2,2}` | {0,1} | **创建失败** | — | — | — | — |

- `{2,2}` 失败原因：ch1 的 `mask<<1 = {1,2}` 与 ch0 的 {0,1} 在块 1 上冲突，而 `j` 只扫 0、1，最终 `channel_id < 0` → `ESP_ERR_NOT_FOUND`（`rmt_tx.c:152`）。
  这也是"ch0 想拿 96 就必然杀掉 ch1"的源码级解释。
- **关键推论【推断】**：帧率由较慢的通道决定，而两通道全程并行，所以 `{1,2}`/`{1,3}` 的额外内存**对本项目毫无价值**。想要 ≥60 Hz 就**必须** 2 个通道，于是补数窗口**必然**是 30 µs。这是 C3 上该方案的物理下限，不是调参能绕过的。
- `{1,2}`/`{1,3}` 会占用原本属于 RX ch2 的内存块 2，**顺带废掉一路 RX 通道**（影响 §6 的环回自检方案，见 §6 第 2 项）。

### 1.5 补不及时会怎样（【文档】+【源码】）

官方文档 FAQ（`rmt.html#faq`，"Why the RMT transmits more data than expected?"）原文：

> "the hardware transmitter might read from the memory before the encoder has written to it. Consequently, the transmitter would end up **sending outdated data**. Although it's not possible to instruct the transmitter to pause and wait, this issue can be mitigated by ..."
> - Increase `mem_block_symbols`, **in steps of 48**.
> - Place the encoding function in the IRAM.
> - Enable `with_dma` if DMA is available.
> - **Install the RMT driver on a separate CPU core** ...（e.g. WiFi, Bluetooth）

源码侧一致：`rmt_ll_tx_enable_wrap(..., true)`（`rmt_tx.c:334`）始终开启环形回绕，驱动只靠一个 duration=0 的 "EOF symbol"（`rmt_tx_mark_eof()`，`rmt_tx.c:602-626`）告诉硬件"到此为止"。指针越过 EOF 之前若没被重填，硬件就**继续回绕重播内存里残留的旧 symbol**。

因此失效形态是：

- **不崩溃、不报错、不丢帧计数**——事务仍然"成功完成"，`on_trans_done` 照常触发，`num_symbols` 也不异常（驱动自己数的是它写进去的数量）。
- 表现是**该条灯带在出错位置之后颜色错乱**（symbol 被多发了，WS2812 把多余位当成后续像素的数据），或**整条停在上一帧的颜色**。
- 8 条灯带里只有正在发送的那 1–2 条受影响；下一次刷新可能又正常 → 表现为"偶发闪一下"。

> 【推断】这也解释了为什么这类问题在现场极难复现：它不落在任何可统计的计数器里，除非专门做环回校验（§6 第 2 项）。

### 1.6 CPU 成本（【推断】，需实测）

- 阈值中断 800 次/帧 + 完成中断 8 次/帧，80 Hz → 约 **6.5 万次/s**。
- 两个 TX 通道是用 `esp_intr_alloc_intrstatus(..., ESP_INTR_FLAG_SHARED, ...)` 挂到**同一个 `ETS_RMT_INTR_SOURCE`** 上的两个共享 handler（`rmt_tx.c:311-314`、`rmt_private.h:62-66`）。一次中断会**依次调用两个 handler**（另一个读状态后立即返回），入口开销翻倍。
- 24 个 symbol 的纯拷贝 + 队列/寄存器操作，按 160 MHz 估 **1–2 µs/次** → **10–20 % CPU 常驻**。
- 若用 `bytes_encoder`（RGB 现场展开），ISR 里还要做 24 次查表/移位，成本约再翻倍。**所以必须预编码成 symbol 数组 + `copy_encoder`**（§5.5）。

另外 `components/esp_driver_rmt/src/rmt_common.c:224-235`：非 DMA 模式下驱动持有 `ESP_PM_CPU_FREQ_MAX` 锁。若开 `CONFIG_PM_ENABLE`，**只要通道处于 enable 状态，CPU 就不许降频**——对时序是好事，对功耗是坏事。这也解释了为什么"每条灯带之间 `rmt_disable` 再 `rmt_enable`"会顺带放开降频（见 §2.4 的对比）。

## 2. `rmt_tx_switch_gpio` 在 v5.5.3 的确切语义

### 2.1 只能在通道关闭时调用（【源码】+【官方单测】）

`components/esp_driver_rmt/src/rmt_tx.c:1135-1174`：

```c
esp_err_t rmt_tx_switch_gpio(rmt_channel_handle_t channel, gpio_num_t gpio_num, bool invert_out)
{
    ...
    // only can switch the GPIO when it's in INIT state
    rmt_fsm_t expected_fsm = RMT_FSM_INIT;
    if (atomic_compare_exchange_strong(&channel->fsm, &expected_fsm, RMT_FSM_WAIT)) {
        // Disable the old GPIO
        if (tx_chan->base.gpio_num >= 0) {
            gpio_output_disable(tx_chan->base.gpio_num);
            esp_gpio_revoke(BIT64(tx_chan->base.gpio_num));
        }
        // Reserve the new GPIO ... gpio_func_sel / esp_rom_gpio_connect_out_signal
    } else {
        ESP_RETURN_ON_FALSE(false, ESP_ERR_INVALID_STATE, TAG, "channel is not in init state");
    }
```

- `RMT_FSM_INIT` 只能由 `rmt_tx_disable()` 到达（`rmt_tx.c:872`）。**通道一旦 `rmt_enable()` 过，就必须先 `rmt_disable()`。**
- 没有任何"下一次传输生效"的延迟机制：它就地改 GPIO Matrix，改完立刻返回。
- 官方单测把这个顺序写死：`components/esp_driver_rmt/test_apps/rmt/main/test_rmt_tx.c:738-741`
  ```c
  TEST_ESP_ERR(rmt_tx_switch_gpio(tx_channel, TEST_RMT_GPIO_NUM_B, false), ESP_ERR_INVALID_STATE);
  TEST_ESP_OK(rmt_disable(tx_channel));
  TEST_ESP_OK(rmt_tx_switch_gpio(tx_channel, TEST_RMT_GPIO_NUM_B, false));
  TEST_ESP_OK(rmt_enable(tx_channel));
  ```

**⇒ 不存在"帧中切换"或"截断半帧"的可能**：想切就必须先停机，停机就必然中止当前事务（`rmt_tx_disable()` 在 `RMT_FSM_RUN` 状态下会 `rmt_ll_tx_stop()` 并回收 `cur_trans`，`rmt_tx.c:823-864`）。所以切换点只能是**两次 transmit 之间**，而且必须等 `on_trans_done` 或 `rmt_tx_wait_all_done()` 返回后再切。

### 2.2 切换瞬间的输出电平（【官方单测】给出直接答案）

`test_rmt_tx.c:743-749`：

```c
// note: the IO level is 1 before the transaction, because the GPIO level will be inherited from the eot_level
TEST_ASSERT_EQUAL(1, gpio_get_level(TEST_RMT_GPIO_NUM_B));
```

即：`tx_transmit_config_t::eot_level` 在 `rmt_tx_do_transaction()` 里通过 `rmt_ll_tx_fix_idle_level(hal->regs, channel_id, t->flags.eot_level, true)`（`rmt_tx.c:759`）被固化成"空闲电平"。切换后新引脚**立刻输出这个空闲电平**，不需要等到下一次 transmit。

- 本项目 `eot_level = 0` ⇒ 新灯带数据线在切换瞬间被驱动为**低**。
- WS2812 的"复位"要求低电平（V5 约 >280 µs，老版 >50 µs）。切换发生在两条灯带之间，被切走的灯带一直保持低直到它下一次被选中（≈12 ms），**天然满足复位**，不需要为每条灯带单独预留 reset 时间——这一点直接影响 §4 的时间账。

### 2.3 真正的毛刺风险：旧引脚变成高阻（【源码】+【推断】）

`gpio_output_disable()` 清 `GPIO.enable` 位 → 焊盘输出使能关闭 → **高阻**。
C3 的 `func_out_sel_cfg` 有 `oen_sel` 位（`components/soc/esp32c3/register/soc/gpio_struct.h:320-329`），而 ROM 版 `esp_rom_gpio_connect_out_signal` 不写该位（`components/esp_rom/patches/esp_rom_gpio.c` 只对 ESP32/S2 做了替代实现，就是为了避开"先开输出再连信号"的毛刺）【推断：C3 上 `oen_sel` 保持 0，焊盘 OE 仍由 `GPIO_ENABLE` 决定】。
所以旧引脚在切换后是**悬空输入**，不是"继续输出低"。

后果：8 条线里任意时刻只有 2 条被驱动，**另外 6 条各悬空约 9 ms**。WS2812 的数据输入是高阻 CMOS 输入，长线悬空会拾取噪声；一旦在复位窗口内出现足够宽的跳变，可能被当成数据位吞掉 → 该条灯带颜色整体错位。

**⇒ 硬件上每条数据线必须有下拉（10 kΩ）+ 串阻（330–470 Ω）。这不是"建议"，是本方案的必要条件。**

另一处小毛刺风险：`rmt_tx_switch_gpio()` 里有 `ESP_LOGD`（`rmt_tx.c:1170`）。若运行时日志级别是 Debug，每次切换会多出几十 µs 的串口输出，直接吃掉帧时间预算。**发布固件与调试固件都必须把该组件的日志压到 INFO 以下。**

### 2.4 更便宜的替代：一信号扇出 4 个 GPIO，只切输出使能

这条路 `research/hardware.md` §1.4 已经提出，这里给出源码级依据与量化对比：

- GPIO Matrix 允许**同一个外设信号接到多个焊盘**（`esp_rom_gpio_connect_out_signal()` 每个引脚独立配置，互不影响）。初始化时把 TX0 的 `tx_sig`（`RMT_SIG_OUT0_IDX`）接到 4 个引脚，TX1 的接到另 4 个。
- C3 上焊盘 OE 由 `GPIO_ENABLE` 决定（`oen_sel = 0`，见 §2.3），所以运行时切换 = 一次 `gpio_output_disable(A); gpio_output_enable(B);`，**两条寄存器写，亚微秒级**。
- **通道全程保持 enabled**：不触发 `rmt_disable/rmt_enable`，不排空事务队列，不反复申请/释放 PM 锁，不重配 GPIO Matrix，不需要 `esp_gpio_reserve/revoke`。

| 维度 | `rmt_tx_switch_gpio` | 扇出 + OE 切换 |
|---|---|---|
| 调用前提 | 必须先 `rmt_disable()`（通道回 INIT） | 通道可一直 enable，只需事务已结束 |
| 单次开销 | disable + 矩阵改写 + enable（含 spinlock、CAS、PM 锁）≈ 5–20 µs【推断】 | 两次寄存器写，<1 µs |
| 高阻窗口 | 切换那几 µs 内旧脚悬空 | 同（但可"先开后关"，做到零悬空） |
| 与 `CONFIG_PM_ENABLE` | 每条之间放开 CPU 降频锁 → 唤醒抖动 | 全程持锁，CPU 稳定 160 MHz |
| 风险 | 依赖驱动的 FSM 状态机 | 依赖"多引脚同信号 + OE 门控"这一未文档化用法；**必须确认同一时刻只有一个 OE 打开**，否则两条灯带收到同一份数据 |

**建议**：主路径用"扇出 + OE"，把 `rmt_tx_switch_gpio` 作为调试期 A/B 的对照实现（它更"官方"，但更慢、状态机更重）。两者都必须在 §6 第 3 项里上板验证。

## 3. 单核 C3 上 BLE 与 RMT 补数 ISR 的相互影响

### 3.1 中断层级模型（【源码】）

C3 是单核 RISC-V，IDF 在 C3 上给外设分配的优先级实际只用到 **1–3 级**（BLE 控制器就是 3 级），而 **4 级是临界区/异常层级**：

- `components/riscv/include/riscv/rv_utils.h:71` → `#define RVHAL_EXCM_LEVEL 4`
- `components/freertos/FreeRTOS-Kernel/portable/riscv/port.c:481-492`：
  ```c
  UBaseType_t xPortSetInterruptMaskFromISR(void) {
      int_level = RVHAL_EXCM_LEVEL;                 // = 4
      prev_int_level = rv_utils_set_intlevel_regval(int_level);
      return prev_int_level;
  }
  ```
- `port.c:596-627`：`vPortEnterCritical()` / `vPortExitCritical()` 就是上面这对函数的嵌套包装。

**⇒ `portENTER_CRITICAL` 把中断阈值抬到 4，屏蔽 1/2/3 级全部外设中断。** 这与 RMT 配到哪一级**无关**：临界区里 RMT ISR 一定进不来。

### 3.2 RMT 中断自己的属性（【源码】）

- `components/esp_driver_rmt/src/rmt_private.h:78` → `#define RMT_ALLOW_INTR_PRIORITY_MASK ESP_INTR_FLAG_LOWMED`（= LEVEL1|2|3）。
- `rmt_private.h:62-66`：`CONFIG_RMT_TX_ISR_CACHE_SAFE` 关闭时只用 `ESP_INTR_FLAG_SHARED`；开启时叠加 `ESP_INTR_FLAG_IRAM`。
- `rmt_tx.c:306-315`：优先级由 `intr_priority`（用户可配，0 = 自动从 1/2/3 里挑）决定，且**一旦设定不可改**。
- `rmt_tx.c:311-314`：两个 TX 通道共享同一个中断源（`ETS_RMT_INTR_SOURCE`），一次中断触发两个 handler。
- `components/esp_driver_rmt/linker.lf:4-10`：`RMT_TX_ISR_HANDLER_IN_IRAM` 默认 `y`，把 `rmt_tx_default_isr`、`rmt_isr_handle_tx_threshold`、`rmt_isr_handle_tx_done`、`rmt_tx_do_transaction`、`rmt_encode_check_result`、`rmt_tx_mark_eof` 全部放 IRAM。`rmt_encoder_copy.c` 的函数由 `RMT_ENCODER_FUNC_ATTR` = `IRAM_ATTR`（`rmt_encoder.h:75`，`Kconfig` 默认 `y`）覆盖。

**⇒ 把 `rmt_tx_channel_config_t::intr_priority` 显式设为 3**，RMT 就与 BLE 控制器同级，BLE 的 ISR 无法抢占它（同优先级不抢占），反之亦然。这是能免费拿到的一个确定性改进。默认 `0` 时可能被分到 1 级，被 BLE 无谓地打断。

### 3.3 BLE 侧（【源码】）

- 控制器 ISR：`components/bt/controller/esp32c3/bt.c:856-873`
  ```c
  p.flags = ESP_INTR_FLAG_LEVEL3 | ESP_INTR_FLAG_IRAM;
  ```
  即 **LEVEL3 + IRAM**。与"RMT 设成 3 级"同级。
- 控制器代码默认在 ROM+IRAM，不在 flash：`components/bt/controller/esp32c3/Kconfig.in:521-530`（`BT_CTRL_RUN_IN_FLASH_ONLY` 默认 `n`，开启后"Bluetooth may not work properly during erasing flash"）。**保持默认**，否则 BLE 自己会在 flash 操作时掉链子。
- NimBLE host 的"硬件临界区"：`components/bt/host/nimble/nimble/porting/npl/freertos/src/npl_os_freertos.c:1133-1153`
  ```c
  npl_freertos_hw_enter_critical(void) { ++hw_critical_state_status; portENTER_CRITICAL(&ble_port_mutex); ... }
  ```
  **⇒ NimBLE host 每次进出临界区，都在整核级别屏蔽 RMT ISR。** 单次很短（µs 量级），但 host 的 list/事件处理会频繁调用。

### 3.4 会不会撕开 30 µs 的窗口

分三件事说清楚：

1. **BLE 控制器 ISR 抢占**：可以消除。`intr_priority = 3` 后同级不抢占。
2. **FreeRTOS/NimBLE 临界区**：**不能消除**。任何 `portENTER_CRITICAL` 都屏蔽全部外设中断，C3 只有一个核，无处可躲。
3. **命中概率**：官方**没有任何文档**说明 BLE 控制器或 NimBLE host 的临界区/ISR 的最长持续时间。ESP-IDF FAQ 只笼统地把 "WiFi, Bluetooth" 列为"interrupt heavy peripherals"，并建议"换一个核"，而 C3 **没有第二个核**。

**⇒ 结论：这是一个必须上板测量的开放项，不能靠读文档判定（§6 第 1 项）。** 可用的间接证据与缓解手段：

- 缓解 A：把 WS2812 位周期从 1.25 µs 放宽到数据手册允许的上限附近（约 1.45–1.55 µs），窗口同比放大 16–24 %，代价是帧率同比下降（§4）。
- 缓解 B：**不做全帧重绘**。只重绘内容变化的灯带（ticket 里"按需重绘"），把 800 次补数/帧降到实际需要的量，直接降低命中概率。
- 缓解 C：把 BLE 连接间隔调大（15 ms → 30 ms），减少每次连接事件的机会；但配网/实时性要另算。

### 3.5 cache / flash 风险（【文档】+【源码】）

官方文档 `rmt.html#cache-safe`：

> "By default, the RMT interrupt is deferred when the Cache is disabled for reasons like writing or erasing the main Flash. ... What is worse, when the RMT transaction relies on **ping-pong** interrupt to successively encode or copy RMT symbols, **a delayed interrupt can lead to an unpredictable result**."

`components/esp_driver_rmt/Kconfig:31-39`：`CONFIG_RMT_TX_ISR_CACHE_SAFE` **默认 `n`**，开启后 `select RMT_TX_ISR_HANDLER_IN_IRAM` + `select RMT_ENCODER_FUNC_IN_IRAM`，并让中断带 `ESP_INTR_FLAG_IRAM`。

`components/spi_flash/Kconfig:86-102`：`SPI_FLASH_AUTO_SUSPEND` **默认 `n`**，所以上面那个 `if !SPI_FLASH_AUTO_SUSPEND` 的条件成立，`CONFIG_RMT_TX_ISR_CACHE_SAFE` 是**可见且可设**的（不会被强制为 n）。

**⇒ 必须显式开 `CONFIG_RMT_TX_ISR_CACHE_SAFE=y`。** 否则只要 BLE 侧往 NVS 写一次绑定信息 / 应用写一次日志分区，那一次 erase（数十 ms 量级）里的所有补数中断都会迟到 → 那一帧必错。
**⇒ 开了之后必须自查**：ISR 里调用的 `xQueueSendFromISR` 等 FreeRTOS 函数默认在 IRAM（`CONFIG_FREERTOS_PLACE_FUNCTIONS_INTO_FLASH` 默认关），但**自己注册的 `on_trans_done` 回调和它调用的函数必须自己保证在 IRAM**（`rmt_tx.h:20-24`、`:131-134` 明确写了这条约束）。本项目建议 `on_trans_done` 只做一次 `xSemaphoreGiveFromISR`，且该函数用 `IRAM_ATTR` 声明。

`SPIRAM`：C3FH4 **没有 PSRAM**，这条风险不存在；但反过来说，**9.6 KB/条 × 双缓冲的预编码数组必须放内部 SRAM**（C3 约 400 KB SRAM，可承受）。

## 4. 时间账与可行性

### 4.1 单条 100 颗

- 100 × 24 bit = **2400 symbol**
- WS2812B 位周期 1.25 µs（T0H 0.4 + T0L 0.85 / T1H 0.8 + T1L 0.45）→ **3.00 ms**
  【注：这是 Worldsemi WS2812B 数据手册的典型值，本仓库未存档该手册，属外部一手资料。】

### 4.2 一帧

| 项 | 值 |
|---|---|
| 每通道 4 条串行 | 4 × 3.00 = **12.00 ms** |
| 8 次切换开销（扇出+OE 方案）【推断】 | 8 × ~5 µs = 0.04 ms；回调→任务→`rmt_transmit` 路径按 20–50 µs/次估 **0.16–0.40 ms** |
| 每条之间单独预留 reset | **不需要**：被切走的灯带自己保持低约 12 ms ≫ 280 µs（§2.2） |
| **合计** | **12.2–12.4 ms** |
| **帧率** | **80.6–82.0 Hz**（理论上限 83.3 Hz） |

若改用"每帧末尾统一 reset 300 µs"：12.5–12.7 ms → 78.7–80 Hz，差别不大；若做成"每条之间都 reset"：14.4 ms → **69.4 Hz**（不必要，别这么做）。

### 4.3 判定

- **≥60 Hz 感知：能，余量约 27 %**（16.7 ms 预算 vs 12.3 ms 实测预期）。
- **76–83 Hz 目标：能，但余量只有 7–8 %**（13.2 ms 预算 vs 12.3 ms）。任何"每条多 200 µs"的实现失误（比如每条都插 reset、或切换走了 `rmt_tx_switch_gpio` 的重路径、或日志没关）就会掉到 76 Hz 以下。
- **抖动的可感知性**：WS2812 自身的复位窗口是几百 µs 量级，帧间抖动 <1 ms 基本不可见；真正会被看见的是**8 条灯带之间的 12 ms 相位差**——快速动画（>2 帧/次的位移）会出现"波浪扫过"，这是分组串行的固有代价，调度上只能靠"同组内相邻灯带在地理上不相邻"来掩盖。

### 4.4 放宽位周期能换什么（可选旋钮）

补数窗口与位周期**成正比**，帧率**成反比**：

| 位周期 | 24 symbol 窗口 | 一帧 (8 条) | 帧率 |
|---|---|---|---|
| 1.25 µs（标称） | 30 µs | 12.0 ms | 83.3 Hz |
| 1.40 µs | 33.6 µs | 13.4 ms | 74.4 Hz |
| 1.50 µs | 36.0 µs | 14.4 ms | 69.4 Hz |
| 1.55 µs（≈手册上限） | 37.2 µs | 14.9 ms | 67.2 Hz |

【推断】这是**唯一**能在"2 通道"约束下稍微放大实时余量的软件旋钮，但最多买到 24 %，且每 1 % 窗口都要用 1 % 帧率换。若 §6 实测显示 30 µs 不够，1.40–1.45 µs 是性价比拐点（仍有 ~74 Hz）。

## 5. 替代方案对比（给结论）

### 5.1 I2S 并行 —— C3 上不可用（【源码】）

- `soc_caps.h:211-223`：`SOC_I2S_NUM = 1`，`SOC_I2S_PDM_MAX_TX_LINES = 2`，无任何 `SOC_LCD_*` / parallel 相关宏（对 C3 soc_caps 全量 grep `LCD` 无命中）。
- ESP32 上那种 "I2S parallel (i2s_lcd)" 依赖 LCD_CAM 外设，C3 没有。I2S 的 TDM 只是"一条线里的多个时隙"，不能变成多条线。
- PDM TX 虽有两路，但输出是硬件 sigma-delta 调制的结果，**无法指定任意 bit 时序**，不能编码 WS2812。

**结论：排除。C3 用 I2S 最多带 1 条灯带。**

### 5.2 SPI MOSI 编码（1 bit → 3 bit）—— 可行但救不了 8 路（【源码】）

- 编码方式：0 → `100`，1 → `110`，SPI 时钟 2.4 MHz（0.4167 µs/bit）→ 每个 WS2812 位 1.25 µs。
  相位误差：T1H = 2 bit = 833 ns（手册 800±150）、T1L = 1 bit = 417 ns（450±150）、T0H = 417 ns（400±150）、T0L = 833 ns（850±150）——**全部在容差内**，这是 FastLED 一类库的标准做法。
- 但 C3 只有 **1 个通用 SPI 主机**（`SOC_SPI_PERIPH_NUM = 2`，其中 SPI0/1 归 flash）→ 一条 MOSI = 一条灯带。**无法覆盖 8 条。**
- 优点：DMA 驱动的，零 ISR 负担，100 颗只要 1 ms。

**结论：单线方案排除。** 真正有意义的是下一条。

### 5.3 四线 QIO SPI 并行 —— 硬件/驱动都允许，但属自研，风险最高

- `SOC_SPI_PERIPH_SUPPORT_MULTILINE_MODE(host_id)` 对 C3 恒为 1（`soc_caps.h:325`），即 SPI2/FSPI 支持多线模式。
- `components/esp_driver_spi/src/gpspi/spi_master.c:1128-1129` 只禁止"多线 + 3-wire"和"多线 + 全双工"，**半双工纯 TX 的 QIO 是允许的**：
  ```c
  SPI_CHECK(!((trans_desc->flags & (SPI_TRANS_MODE_DIO | SPI_TRANS_MODE_QIO)) && !is_half_duplex), ...);
  ```
- 数据组织：QIO 每个字节拆成两个 4-bit 半字节（先高后低），**每个时钟 4 条线各得 1 bit**。把 4 条灯带的下一批位拼进一个字节即可：`(b0<<7)|(b1<<6)|(b2<<5)|(b3<<4)|(b0'<<3)|(b1'<<2)|(b2'<<1)|b3'`。
- 时间账：每条灯带 2400 位 × 3 SPI bit = 7200 bit，按 0.4167 µs → **3 ms 送 4 条**；8 条两轮 = **约 6 ms/帧（≈166 Hz）**，且 DMA 全程无 CPU 参与、无 ISR 窗口。
- 代价与风险：
  1. **没有官方例程**，要自己算位交织（可预计算 LUT，1200 B/轮的 tx buffer）。
  2. 4 条数据线在 `spi_bus_initialize()` 时固定，8 条灯带需要**两轮之间重接 GPIO Matrix**（`gpio_matrix_out` 改写），这是未文档化用法。
  3. 若要把 8 条全放进"4 线"的同一轮，不可能（只有 4 条线）。
  4. 占用 4 个引脚 + 需要 GPIO Matrix 绕开 C3 默认的 FSPI IO_MUX 引脚（GPIO2/4/5/6/7/10，与灯带引脚重叠）。

**结论：它是唯一能同时解决"帧率"和"30 µs 实时窗口"的方案（166 Hz + 零 ISR），但实现风险显著高于 RMT。建议作为 ticket 之外的独立 spike 并行验证；在它跑通之前，RMT 4+4 仍是主线。**

### 5.4 关中断 bit-bang 8 路并行 —— 能算，但不能这么用

- 可行性：8 个引脚可以**任意分布**，一次 `GPIO_OUT_W1TS/W1TC` 写就能同时翻 8 位（掩码写寄存器对位位置没有连续性要求）。所以"8 路真并行"在寄存器层面是成立的，一轮 3 ms，8 条一轮搞定，帧率可达 300 Hz。
- 代价：3 ms 全程关中断。80 Hz 下 3 ms/12.5 ms = **24 % 的时间整核失去中断响应**。
  - BLE：连接间隔 15 ms 时，每个连接事件约 24 % 概率被整段吞掉；再叠加调度抖动，**丢包/连接不稳是必然的**，supervision timeout 迟早触发。
  - 同时 `esp_timer`、USB Serial/JTAG、FreeRTOS tick 全部延迟 3 ms。
  - 代码必须整段 `IRAM_ATTR` + 关中断，且时序要靠 `nop` 校准；C3 上若开了 flash cache miss，3 ms 会变成不确定长度。
- 若一定要用，只能"4 路 × 2 轮"把单次关中断降到 3 ms、总占比不变，或者只在对 BLE 断连可接受的配网/演示模式下启用。

**结论：只作为 RMT 方案彻底失败时的兜底，且要接受 BLE 不可用。**

### 5.5 双缓冲 / 预编码 —— 不是可选项，是必做项

- RMT 的硬件缓冲只有 48 word，**没有"第二级缓冲"可加**；`trans_queue_depth` 排的是**事务**，不是 symbol，不改变 30 µs 窗口。
- 但可以把 ISR 里的工作压到最小：**先把 RGB 预编码成 `rmt_symbol_word_t[2400]`，用 `copy_encoder` 发送**（`rmt_encode_copy()` 在 ISR 里只做 24 次数组拷贝，`rmt_encoder_copy.c:61-65`）。相比 `bytes_encoder` 在 ISR 里现场展开 3 个字节，省掉全部查表/移位。
- 双缓冲：每条通道 2 个 9.6 KB 缓冲（一条在发、一条在编码下一帧），共 **4 × 9.6 = 38.4 KB** 内部 SRAM。若只想省内存，每通道 1 个缓冲（在等待 `on_trans_done` 的那几 µs 里编码下一条）也够，因为串行驱动本来就有 3 ms 的空档可以编码。
- 编码 2400 个 symbol 的成本【推断】：1200 次查表 + 2400 次写，约 50–100 µs，完全能藏进 3 ms 空档。

## 6. 必须上板实测的项

| # | 测什么 | 怎么测 | 判定阈值 | 为什么必须测 |
|---|---|---|---|---|
| 1 | **RMT 补数 ISR 是否被撕开**（核心项） | 用一个空闲 GPIO 在 `on_trans_done` 里翻转（仅定位帧边界不够），主口径用第 2 项的环回；辅助：在阈值 ISR 前后各加一次 `GPIO.out ^= mask` 的临时补丁版驱动（`rmt_isr_handle_tx_threshold` 首尾），逻辑分析仪量脉宽 | 单次 ISR 入口延迟 **< 20 µs**（留 10 µs 余量），**10 分钟内 0 次 > 30 µs** | 官方无任何 BLE 临界区时长文档；C3 无法"换核" |
| 2 | **输出位流正确性（端到端）** | 把某条数据线并到一路 **RMT RX** 通道（C3 有 ch2/ch3，用 `{1,1}` 内存配置时块 2/3 可用），`rmt_receive()` + `signal_range_max_ns` 解析，逐 symbol 比对期望 | 每帧 **0 个 symbol 偏差**，连续 30 min | 这是唯一能抓住"静默重播旧数据"的手段（§1.5） |
| 3 | **切换毛刺与悬空** | 逻辑分析仪同时接 TX0 组 4 个引脚，量：旧脚释放瞬间的电平/高阻、新脚起始电平、首颗 LED 首位是否完整；再用 10 kΩ 上拉临时替换下拉，看是否出现非预期高电平（验证悬空） | 旧脚不得出现 >100 ns 的高电平尖峰；新脚起始必须是稳定低 ≥ 280 µs | `gpio_output_disable` 后高阻是源码确定行为（§2.3） |
| 4 | **首颗 LED 是否吞位/错色** | 静态图案：第 0 颗设为与其他显著不同的颜色（如全红，其余全蓝），8 条都这样；肉眼+摄像头逐条检查 | 100 % 正确，重复 100 次切换 | 切换发生在两次 transmit 之间，首 symbol 前可能有 µs 级空洞 |
| 5 | **帧率与抖动** | 帧起点翻一个空闲 GPIO，逻辑分析仪统计周期分布（1 万帧） | **均值 ≥ 76 Hz，p99 ≤ 16.7 ms，最大间隔 ≤ 20 ms** | 对 76 Hz 只剩 7–8 % 余量（§4.2） |
| 6 | **BLE 压力下的稳定性** | 主机以连接间隔 15 ms、每事件多条 `notify`（最大 MTU 负载）持续 1 h；同时跑全速动画；记录丢包/断连/重连次数 | **0 次断连**，通知丢包率 < 0.1 % | 直接压迫 1、2 项 |
| 7 | **NVS / flash 写期间的错色** | 动画过程中每 5 s 写一次 NVS；分别测 `CONFIG_RMT_TX_ISR_CACHE_SAFE = n / y` | `y` 时 **0 次错色**；`n` 时应能复现错色（作为对照，证明该项配置有效） | 官方文档明确"ping-pong + cache disabled = unpredictable result" |
| 8 | **两通道内存配置真的建得起来** | 依次 `rmt_new_tx_channel(mem_block_symbols=48)`、再 `(96)` 或 `(144)`，打印返回码与 `rmt_get_channel_id()` | `{1,2}`/`{1,3}` 返回 `ESP_OK` 且 channel_id 分别为 0/1；`{2,2}` 必须返回 `ESP_ERR_NOT_FOUND` | §1.4 的组合来自源码推导，硬件指针是否真的跨块回绕未验证 |
| 9 | **`intr_priority = 3` 的实际效果** | 与 `0`（默认）对比第 1 项的延迟分布 | 3 级应显著降低 >10 µs 的尾部次数 | `RMT_ALLOW_INTR_PRIORITY_MASK` 允许 3，但 BLE 同级抢占行为需实测 |
| 10 | **`rmt_tx_switch_gpio` vs 扇出+OE** | 两套实现各跑 1 h，比帧率、比第 3/4 项 | 扇出+OE 的均值帧率应高 0.2–0.5 Hz；两者都不得有毛刺 | 决定最终实现路径 |
| 11 | **位周期放宽的收益** | 1.25 / 1.40 / 1.50 µs 各测第 1、5 项 | 找到"窗口够大且帧率仍 ≥ 70 Hz"的拐点 | §4.4 的旋钮是唯一的软件缓解 |

> 第 2 项的硬件前提：数据线要能被 RX 通道采到——直接并线即可（WS2812 输入是高阻，并在首颗 LED 前加 Y 点），或临时用一根短线把该 GPIO 接到另一个 GPIO 做环回。注意 `{1,2}/{1,3}` 会占用块 2，环回只能用块 3。

## 7. 风险与缓解（按严重度）

| 风险 | 触发条件 | 后果 | 缓解 |
|---|---|---|---|
| **30 µs 窗口被临界区吃掉** | BLE 控制器/NimBLE host 任一 `portENTER_CRITICAL` > 30 µs | 某条灯带帧尾重播旧数据 → 偶发错色 | `intr_priority = 3`；按需重绘；位周期放宽到 1.4 µs；不行就上 §5.3 QIO SPI |
| **cache 关闭期间 ISR 被推迟** | NVS 写、OTA、日志落盘 | 必错色（可复现） | `CONFIG_RMT_TX_ISR_CACHE_SAFE=y` + 回调 `IRAM_ATTR` |
| **6 条线长期悬空** | 没有下拉电阻 | 噪声被当数据位吞掉 → 整体错色 | 每条线 10 kΩ 下拉 + 330–470 Ω 串阻 |
| **帧率不足 76 Hz** | 切换路径走了 `rmt_tx_switch_gpio`；每条都插 reset；日志没关 | 掉到 69–74 Hz | 扇出+OE；不插逐条 reset；运行时 `esp_log_level_set("rmt", ESP_LOG_INFO)` |
| **两通道 ISR 共享入口翻倍** | 无法避免 | +5–10 % CPU | 接受；把补数窗口的余量留够 |
| **`{1,2}` 滥用导致 RX 不可用** | 想"顺手"给 ch1 加内存 | 块 2 被占，环回自检只能用块 3 | 默认 `{1,1}`，没有收益不要动 |
| **单核无第二核可迁** | 官方 FAQ 的第一建议失效 | 无退路 | 这就是为什么要有 §5.3 的并线备选方案 |

## 8. 明确未被证实 / 待澄清

1. **BLE 临界区与 ISR 的最长持续时间**：v5.5.3 源码里没有常量或文档给出上界。本文只能给出机制（`portENTER_CRITICAL` → intlevel 4）与测量方法，**不给数值结论**。
2. **C3 上 `oen_sel` 恒为 0**：由 `esp_rom/patches/esp_rom_gpio.c` 只覆盖 ESP32/S2 反推，未在 TRM 中逐字确认。若该位被 ROM 置 1，则"扇出+OE 切换"不成立（OE 会由外设信号决定），必须改回 `rmt_tx_switch_gpio`。**这是 §2.4 方案的前置条件，属于上板第一个要验证的寄存器读回值。**
3. **`{1,2}` / `{1,3}` 的内存跨块回绕**：驱动允许，但硬件 `mem_size` 指针是否严格按 `mem_size*48` 回绕，需要实测（§6 第 8 项）。
4. **WS2812B 的位周期上限**：本文采用 1.25 µs 标称、±150 ns/相位、整体 ±600 ns 的常见手册值；**具体批次的数据手册需归档到仓库**，否则 §4.4 的"放宽旋钮"没有依据。
5. **`rmt_disable()` 是否真的重置 encoder**：官方文档（`rmt.html#rmt-encoder`）说 "This function is also called implicitly in `rmt_disable()`"，但 v5.5.3 的 `rmt_tx_disable()`（`rmt_tx.c:810-875`）里**没有** `rmt_encoder_reset()` 调用；实际重置发生在下一次 `rmt_tx_do_transaction()` 开头（`rmt_tx.c:690`）。对功能无影响，但文档与源码不一致，值得记一笔。
